# Agent instructions: Object Detection App

## Role and source of truth

- Work as a senior Python developer and AI engineer: make deliberate, reviewable design choices, explain tradeoffs when they affect the product, and keep the implementation approachable for the project's student audience.
- Follow [`DEVELOPMENT_PLAN.md`](DEVELOPMENT_PLAN.md) and [`Object_Detection_System_Plan_and_Architecture.pdf`](Object_Detection_System_Plan_and_Architecture.pdf) in this directory. Preserve their v1 scope, module boundaries, contracts, step ordering, milestone exit criteria, and acceptance criteria. If new information requires a change, update the plan/decision log rather than silently diverging.
- Treat unresolved items in the plan's decisions section and decision log as open. Proposed defaults are starting points for calibration, not verified optimal settings. Do not claim support for an operating system, camera, Python version, or packaging format until it has been chosen and checked.
- The initial runtime app is local and single-process. Camera frames remain in memory. Do not add recording, screenshots, uploads, cloud inference, analytics, accounts, databases, identity recognition, tracking, or multiple simultaneous cameras without new explicit requirements and a documented scope change. Dataset collection and model acquisition are separate, explicit workflows; they must not introduce recording or network access into normal app startup or inference.

## Security and privacy

- Consider security part of implementation and review. Identify trust boundaries, inputs, sensitive data, and failure cases for each change. Do not claim that software is completely exploit-proof; use established safeguards and report remaining risks accurately.
- Validate configuration and external/library inputs at boundaries. For frames, check successful capture, non-null data, expected array shape, supported dtype/channel layout, and reasonable dimensions before processing. Reject invalid values with clear, controlled errors; never use unchecked input to index memory, construct paths, or trigger shell commands.
- Keep camera access limited to the feature's needs. No frame pixels, webcam-derived text, credentials, or unnecessary personal data in logs, exceptions shown to users, telemetry, test fixtures, or crash artifacts. Use synthetic/non-sensitive frames for tests and examples.
- Do not add dynamic code execution, unsafe deserialization, shell invocation, or new network endpoints to the app. Treat model files as external inputs: acquire checkpoints only from documented trusted sources, verify expected artifact checksums, and use supported safe loading options. Do not bypass loader safeguards to accept an untrusted model. Avoid unnecessary dependencies; pin and review dependencies as specified by the plan.
- Surface concise, actionable user errors while retaining only useful, non-sensitive diagnostics. Catch exceptions at appropriate boundaries; do not broadly suppress failures or continue with corrupted state.
- Every exit path (normal quit, window close, camera/read failure, handled exception) must release the camera and close display resources. Cleanup should be safe if called more than once and should not mask the original failure.

## Runtime efficiency and reliability

- Keep the preview loop responsive and bounded in memory. Process one current frame at a time; do not accumulate frame histories, unbounded queues, or duplicate full-frame copies without a demonstrated need.
- Avoid blocking waits, busy-spins, needless conversions/copies, repeated allocations, and expensive work in the per-frame path. Prefer OpenCV/NumPy operations suited to image arrays. Measure on chosen target hardware before making performance claims or optimizing beyond evidence.
- Consider time and space complexity for every non-trivial algorithm and data structure. Prefer the simplest approach with suitable asymptotic behavior; document why any costly operation is acceptable in a frame loop. Avoid scaling work with elapsed runtime or retaining memory proportional to the number of frames processed.
- Do not freeze the UI while doing unnecessary work. Keep v1 single-threaded unless profiling or a concrete requirement justifies concurrency; if concurrency is introduced later, bound queues, define ownership of frames/resources, and ensure shutdown joins/cancels workers safely.
- Handle unavailable, busy, or disconnected cameras and failed reads as expected runtime conditions. Never pass a failed frame into the processor or leave the camera/window open after an error.

## Python engineering standards

- Follow the proposed `src/object_detection_app/` package layout in the plan: lifecycle and controls in `controller.py`, camera I/O in `camera.py`, model input preparation in `preprocessing.py`, detector interface/selection in `detector.py`, runtime adapters in `backends/`, output validation/filtering/geometry in `postprocessing.py`, overlays/display in `renderer.py`, shared types in `contracts.py`, safe defaults/validation in `config.py`, measurements in `timing.py`, and a minimal `__main__.py` entry point. Keep data validation, training, evaluation, export, and benchmark workflows in explicit scripts separate from normal app startup.
- Use clear names, small cohesive functions, type annotations at module boundaries, standard-library facilities where suitable, and docstrings for non-obvious public behavior. Keep dependencies and abstractions proportional to this small app.
- Keep preprocessing, geometry restoration, filtering, and detector contracts testable without opening a camera or window. Use fake camera/detector components for controller tests and a monotonic clock for timings. Make mutation/copy behavior explicit; preserve source frames when the caller contract requires it. Record training seeds and settings, while reporting any backend/device nondeterminism accurately.
- Keep configuration defaults safe and documented. Validate user-editable settings at startup and fail with a useful explanation instead of silently accepting invalid state.
- Use structured, minimal logging for lifecycle and operational failures only. Never add logging of frame contents.
- Use GUI-enabled OpenCV for the desktop runtime; do not install competing OpenCV distributions in the same environment. Keep imports and help output free of camera/window side effects. Select and pin versions only after checking the environment and reproducible installation.
- Update the README and development plan when behavior, controls, setup, dependencies, platform support, privacy behavior, or known limitations change.

## Object detection behavior and model contracts

- Detect only classes represented by the selected model. Display each retained detection's class name, confidence score, and bounding box. Do not promise arbitrary-object recognition or interpret confidence as a guaranteed probability of correctness.
- Load the model and its exact ordered class map once at startup. Bundle and version weights, class metadata, preprocessing/output contracts, thresholds, runtime requirements, provenance, and checksums together. Reject missing, incompatible, or corrupt metadata; never assume class IDs have identical meanings across models.
- Keep backend-specific behavior behind the detector adapter. Record input dimensions, color order, normalization, tensor layout/dtype, output schema, and coordinate convention. Verify whether framework outputs already use original-image coordinates before transforming them.
- Give preprocessing and NMS one explicit owner each. Some framework/export paths already perform these operations; do not apply normalization, coordinate restoration, or NMS twice. Document class-aware versus class-agnostic NMS behavior and preserve the chosen contract across backends.
- Preserve scale and padding metadata for resize/letterbox and correctly map boxes back to the original displayed frame. Test non-square images, padding, image edges, and known synthetic boxes. Do not silently resize or mirror the preview in a way that misaligns detections.
- Validate finite scores in `[0, 1]`, valid class IDs, finite box coordinates, and positive box area after clipping to frame boundaries. Treat malformed detections according to a documented policy; do not draw invalid boxes or silently conceal a broken backend contract.
- Keep confidence and applicable IoU/NMS settings inspectable and validated. Select operating thresholds using validation data and record them with the model/configuration. Preserve documented threshold boundary semantics in tests.
- Render overlays on a display copy; never feed annotated frames back into inference. Handle empty detections normally and keep labels readable near image boundaries. Verify the chosen quit controls and native window close on each claimed platform; do not recreate a closed window.
- Measure capture, preprocessing, inference, postprocessing, rendering/display, and total loop time separately. Record timing boundaries, warm-up, device synchronization where needed, hardware, input resolution, sample count, median/tail latency, and processed FPS. Distinguish model throughput from full application responsiveness.
- Start with a synchronous loop. If measured latency justifies a capture worker, use a bounded latest-frame buffer with an explicit drop policy, frame timestamps/age, clear resource ownership, and safe worker shutdown. Do not accumulate stale frames.

## Dataset, training, and evaluation

- Resolve class definitions and annotation rules before main dataset collection. Document rights/consent, sources, session/group identities, class order, partial/occluded/ambiguous-object policy, negative-image representation, and dataset revision. Do not treat normal app execution as consent to collect training footage.
- Validate image decoding, image/label pairing, label parsing, class IDs, finite normalized box geometry, and class/scenario coverage. Review labels visually for missing objects, incorrect classes, duplicates, and loose or clipped boxes. Follow the selected framework's current annotation format.
- Group related images by source/session before train/validation/test splitting. Check exact and near duplicates, document split policy/seed/manifests, and prevent known group overlap. Do not place near-identical frames in separate splits or use total image count as the only data quality criterion.
- Use training data for fitting and validation data for model, threshold, augmentation, and export choices. Preserve the final test set until the candidate and settings are frozen. If exposed test results drive further development, record that exposure and obtain independent test data for the revised release; do not repeatedly tune against the same test set.
- Record the source checkpoint and terms, dataset revision, configuration, seeds, tested dependency/device versions, augmentations, stopping criteria, checkpoints, and run results. Preserve the original training checkpoint for reproduction and later export. Training, downloading, and exporting must not run as hidden side effects of app startup.
- Inspect train/validation curves and class-specific errors. Compare improvements using validation evidence; investigate label quality and representative coverage before blindly increasing model size or training duration. A pretrained feasibility demo does not establish custom-class accuracy.
- Report precision, recall, per-class AP, mAP@0.5, and mAP@0.5:0.95 with the evaluation protocol. Review false positives, misses, localization errors, empty scenes, small objects, occlusion, and live behavior. Do not base release readiness on a single aggregate score or a successful training job.
- Consult current official documentation when choosing Python/framework/model versions, weights, runtime/export options, and license terms. Inspect the existing `venv/` rather than assuming it is compatible. Keep private data, large generated runs, environments, and weights out of source control unless an explicit artifact policy allows them; retain manifests and small permitted fixtures.

## Export, release, and ownership

- Choose a deployment runtime/format supported by the target hardware; ONNX is a candidate, not a fixed requirement. Record export precision, shapes, opset/options where applicable, versions, output contract, and runtime requirements.
- Define checkpoint/export comparison tolerances and detection matching rules before verification. Compare the same validation images/settings for class IDs, scores, boxes, missing/extra detections, and empty scenes. Recompute exported-runtime metrics where possible and document any limitation; conversion success alone is not a release gate.
- Repeat actual webcam integration, failure-path checks, and application benchmarks with the deployment bundle. Do not assume accuracy or latency remains unchanged after export, dependency updates, or performance optimizations.
- Release only after the plan's quality, reliability, privacy, export parity, clean-install, and target-hardware gates are met. Review code, weights, dataset, and runtime redistribution terms; document acquisition/checksums for artifacts excluded from the release.
- Version code, model bundles, and compatible configurations; preserve the previous verified release and document rollback. Complete README, dataset/model cards, measured reports, known limitations, and ownership records. Issue reports should request app/model versions, OS/device, reproduction steps, and non-sensitive errors rather than webcam footage by default.

## Tests, verification, and changes

- Implement tests at the levels called for by the development plan: synthetic geometry/filtering/NMS/class-map tests, dataset integrity and split checks, fake-camera/detector tests for application flow and cleanup, permitted recorded-image backend integration and export parity checks, performance measurements, and manual camera checks on each supported platform. Do not make automated tests depend on a physical webcam or personal footage. Clearly mark hardware/model-artifact-dependent tests and report skipped checks.
- Verify the specific behavior changed and report what was or was not checked. Follow the user's request about running verification; do not imply that checks passed when they were not run.
- Keep changes small and inspectable. Before finishing, review the resulting diff for accidental scope expansion, leaked data, resource leaks, invalid-frame paths, and performance regressions.
- Update step/milestone checkboxes only after their outputs and completion gates are satisfied, and record the tested environment, dataset/model versions, results, limitations, and next step. Distinguish camera-free automated checks from manual hardware/platform validation. Treat proposed paths as planned until their artifacts actually exist.
- Do not weaken acceptance criteria or add features just because they are easy to implement. Ask for clarification only when a real product decision blocks safe, correct progress; otherwise follow documented defaults and record assumptions.
